systematic-debugging

遇到任何 bug、测试失败或非预期行为时,先走一遍系统调试的四阶段,而不是直接提修复方案:查根因 → 找模式 → 立单一假设最小验证 → 只改一处修根因。何时用:在你准备说出「问题应该是 X,改一下试试」之前——尤其是在赶时间、已经试过几次修复、或者自己还没完全搞懂的时候。

执行总纲:任何 bug 都先走四阶段:查根因 → 找模式 → 单一假设最小验证 → 只改一处修根因;没做完 Phase 1 就不许提修复,连修三次不成就停下来质疑架构 这份 skill 的执行形态是一条带硬闸口和多条回退边的四阶段主线:铁律 NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST 守住入口,Phase 1 读错误 / 复现 / 查改动、多组件系统先插桩取证、深栈错误反向追数据流,Phase 2 拿可用样例逐条比差异,Phase 3 一次只立一个假设并用最小改动验证——不成就换新假设而不是叠加修复,Phase 4 先有失败测试再只改一处修根因。修复失败时不许硬上第四刀:少于三次回 Phase 1 重新分析,达到三次就停下来和人类搭档讨论架构。红旗话术与搭档的重定向信号是随时生效的两道守护,命中即 STOP 回到 Phase 1。

n01 · S 层 · 语义/知识 · core_principle

Overview

整份 skill 的公理写在这里:乱修既浪费时间又制造新 bug,快速补丁只是把问题盖住;永远先找根因再谈修复,症状式修复本身就算失败。它不是流程步骤,是后面每一步的判据来源。

Random fixes waste time and create new bugs. Quick patches mask underlying issues.

Core principle: ALWAYS find root cause before attempting fixes. Symptom fixes are failure.

Violating the letter of this process is violating the spirit of debugging.

n03 · R 层 · 路由/激活 · activation

When to Use

路由层:任何技术问题都走这套——测试失败、线上 bug、非预期行为、性能问题、构建失败、集成问题。越是赶时间、越是「就一个快修很明显」、越是已经试过好几次,越要走;而「问题看起来简单」「在赶时间」「老板要马上修好」都不构成跳过的理由。

Use for ANY technical issue:

  • Test failures
  • Bugs in production
  • Unexpected behavior
  • Performance problems
  • Build failures
  • Integration issues

Use this ESPECIALLY when:

  • Under time pressure (emergencies make guessing tempting)
  • "Just one quick fix" seems obvious
  • You've already tried multiple fixes
  • Previous fix didn't work
  • You don't fully understand the issue

Don't skip when:

  • Issue seems simple (simple bugs have root causes too)
  • You're in a hurry (rushing guarantees rework)
  • Manager wants it fixed NOW (systematic is faster than thrashing)

触发条件(R 层)

  • 遇到任何 bug、测试失败或非预期行为时,先于提出修复方案 encountering any bug, test failure, or unexpected behavior
  • 在提出修复之前就要进入本流程 before proposing fixes
  • 适用于任何技术问题:测试失败、线上 bug、非预期行为 Use for ANY technical issue:
  • 性能问题、构建失败、集成问题同样适用 - Performance problems
  • 时间压力下尤其要用——紧急状态最容易诱发瞎猜 Under time pressure (emergencies make guessing tempting)
  • 「就一个快修」看起来很明显时,尤其要用 "Just one quick fix" seems obvious
  • 已经试过多次修复、上一次修复没生效时,尤其要用 You've already tried multiple fixes
  • 自己还没完全搞懂问题时,尤其要用 You don't fully understand the issue

Step 1 · Phase 1: Root Cause Investigation RETRIEVE

目标 动手改任何东西之前,先把根因查清楚 BEFORE attempting ANY fix

怎么做

  1. 逐字读错误信息与告警,别跳过——里面常常直接写着解法 They often contain the exact solution
  2. 完整读栈回溯,记下行号、文件路径、错误码 Note line numbers, file paths, error codes
  3. 稳定复现:能否可靠触发?确切步骤是什么?是否每次都发生? Can you trigger it reliably?
  4. 查最近改动:git diff、近期提交、新依赖、配置变更、环境差异 Git diff, recent commits

Step 2 · Phase 2: Pattern Analysis REVIEW

目标 动手前先找出模式:拿能跑通的例子和坏掉的做对照 Find the pattern before fixing

怎么做

  1. If 3+ Fixes Failed: Question Architecture

Pattern indicating architectural problem:

  • Each fix reveals new shared state/coupling/problem in different place
  • Fixes require "massive refactoring" to implement
  • Each fix creates new symptoms elsewhere

STOP and question fundamentals:

  • Is this pattern fundamentally sound?
  • Are we "sticking with it through sheer inertia"?
  • Should we refactor architecture vs. continue fixing symptoms?

Discuss with your human partner before attempting more fixes

This is NOT a failed hypothesis - this is a wrong architecture.
