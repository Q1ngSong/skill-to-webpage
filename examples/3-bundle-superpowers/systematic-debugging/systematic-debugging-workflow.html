Overview

语义/知识节点,不是流程步骤。

Random fixes waste time and create new bugs. Quick patches mask underlying issues.

Core principle: ALWAYS find root cause before attempting fixes. Symptom fixes are failure.

Violating the letter of this process is violating the spirit of debugging.

n03 · R 层 · 路由/激活 · activation

When to Use

路由/激活节点,不是流程步骤。

Use for ANY technical issue:

  • Test failures
  • Bugs in production
  • Unexpected behavior
  • Performance problems
  • Build failures
  • Integration issues

Use this ESPECIALLY when:

  • Under time pressure (emergencies make guessing tempting)
  • "Just one quick fix" seems obvious
  • You've already tried multiple fixes
  • Previous fix didn't work
  • You don't fully understand the issue

Don't skip when:

  • Issue seems simple (simple bugs have root causes too)
  • You're in a hurry (rushing guarantees rework)
  • Manager wants it fixed NOW (systematic is faster than thrashing)

触发条件(R 层)

  • 遇到任何bug、测试失败或非预期行为,在提出修复之前先用本流程 Use when encountering any bug, test failure, or unexpected behavior
  • 任何技术问题都适用:测试失败、生产bug、非预期行为、性能问题、构建失败、集成问题 Use for ANY technical issue:
  • 时间紧迫、'一个小修复'看似显而易见、已经试了好几个修复、上次修复没用、没完全搞懂问题时,更要用本流程 Use this ESPECIALLY when:
  • 问题看似简单、赶时间、经理催办,都不是跳过流程的理由 Don't skip when:

Step 1 · Phase 1: Root Cause Investigation OBSERVE

目标 在提出任何修复方案之前,先彻底调查清楚问题的根本原因 BEFORE attempting ANY fix:

怎么做

  1. 完整阅读报错信息和堆栈,记录行号、文件、错误码 Read stack traces completely
  2. 设法稳定复现问题,明确触发步骤和频率 Can you trigger it reliably?
  3. 检查近期变更:git diff、新依赖、配置、环境差异 Git diff, recent commits
  4. 多组件系统里,先在每个组件边界埋点跑一次收集证据,再判断具体哪层出错 Run once to gather evidence showing WHERE it breaks
  5. 报错在调用栈深处时,向上逐层回溯,直到找到坏值的源头 Keep tracing up until you find the source

规则

  • 未完成Phase1前不能提出修复方案(铁律) you cannot propose fixes

质量标准 0/2

技巧

  • 报错和警告常常直接给出答案,不要跳过 They often contain the exact solution
  • 复现不了就该去收集更多数据,而不是瞎猜 gather more data, don't guess

示例

  • 多层系统诊断示例:分别在workflow、build脚本、keychain、签名命令四层打印诊断信息以定位失败层 codesign --sign "$IDENTITY" --verbose=4 "$APP"

常见翻车

  • 看见症状就想直接下手修,不等于理解了根因 Seeing symptoms ≠ understanding root cause.
  • 以为紧急情况就该跳过流程,实际系统方法反而更快 Systematic debugging is FASTER than guess-and-check thrashing.

治理约束

多组件系统必须先加诊断埋点收集证据,才能提修复方案 BEFORE proposing fixes, add diagnostic instrumentation:

工具

报错在调用栈深处时,参考root-cause-tracing.md的完整反向追溯技巧

Step 2 · Phase 2: Pattern Analysis REASON

目标 修复前先找到问题模式:对比能用的实现和坏掉的实现 Find the pattern before fixing:

怎么做

  1. 在同一代码库里找类似的、能正常工作的代码 Locate similar working code in same codebase
  2. 如果是照着某个模式实现,要把参考实现完整读一遍,不能只扫一眼 Don't skim - read every line
  3. 逐条列出能用的和坏掉的之间的每一个差异,再小也不能忽略 List every difference, however small
  4. 搞清楚这个功能依赖哪些其他组件、设置、环境、假设 What other components does this need?

质量标准 0/1

常见翻车

  • 参考实现太长就想跳读、只学个大概,只会带来一知半解的bug Partial understanding guarantees bugs. Read it completely.

Step 3 · Phase 3: Hypothesis and Testing PLAN ◆ 验证闸口

目标 用科学方法验证假设:提出单一假设、做最小化测试、确认后再继续 Scientific method:

怎么做

  1. 清楚写下'我认为X是根因,因为Y' State clearly: "I think X is the root cause because Y"
  2. 每次只改一个变量,做能验证假设的最小改动 One variable at a time
  3. 不确定时要明说'我不理解X',不要装懂,要去请教或再研究 Don't pretend to know

质量标准 0/1

常见翻车

  • 假设没验证成功就不要在上面继续叠加修复 DON'T add more fixes on top

⇢hypothesis test succeeded →
⇢hypothesis test failed

Step 4 · Phase 4: Implementation GENERATE ◆ 验证闸口

目标 修复根本原因而不是表面症状 Fix the root cause, not the symptom:

怎么做

  1. 先写出能复现问题的失败测试用例,有条件就写自动化测试 MUST have before fixing
  2. 一次只改一个地方,不顺手做额外重构 No bundled refactoring
  3. 验证测试通过、其它测试没坏、问题确实解决了 No other tests broken?

质量标准 0/1

常见翻车

  • 想着先确认修复有效再补测试,其实没测试的修复站不住 Untested fixes don't stick. Test first proves it.
  • 一次改多处会没法判断到底是哪处改动起了作用,还会引入新bug Can't isolate what worked. Causes new bugs.

工具

n05 · S 层 · 语义/知识 · failure_modes

Red Flags - STOP and Follow Process

语义/知识节点,不是流程步骤。

If you catch yourself thinking:

  • "Quick fix for now, investigate later"
  • "Just try changing X and see if it works"
  • "Add multiple changes, run tests"
  • "Skip the test, I'll manually verify"
  • "It's probably X, let me fix that"
  • "I don't fully understand but this might work"
  • "Pattern says X but I'll adapt it differently"
  • "Here are the main problems: [lists fixes without investigation]"
  • Proposing solutions before tracing data flow
  • "One more fix attempt" (when already tried 2+)
  • Each fix reveals new problem in different place

ALL of these mean: STOP. Return to Phase 1.

If 3+ fixes failed: Question the architecture (see Phase 4.5)

语义/知识节点,不是流程步骤。

When Process Reveals "No Root Cause"

流程节点。每个步骤的首行 ⇢ 是进入该步的条件;类型徽章来自语义层的步骤分型,◆ 验证闸口、⏸ 需用户确认;上方弧线是条件跳转(蓝,虚线 = 推断)与重试环(橙);下方外部节点栏里,点线是别的节点供给本步的依赖,橙线是兜底去向;⦿ 是终止点。

If systematic investigation reveals issue is truly environmental, timing-dependent, or external:

  1. You've completed the process
  2. Document what you investigated
  3. Implement appropriate handling (retry, timeout, error message)
  4. Add monitoring/logging for future investigation

But: 95% of "no root cause" cases are incomplete investigation.
