When to Request Review

路由/激活节点,不是流程步骤。

Mandatory:

  • After each task in subagent-driven development
  • After completing major feature
  • Before merge to main

Optional but valuable:

  • When stuck (fresh perspective)
  • Before refactoring (baseline check)
  • After fixing complex bug

Step 4 · Act on feedback CLASSIFY ◆ 验证闸口 隐含步骤

目标 按问题严重度决定后续动作 Act on feedback

怎么做

  1. Critical问题立即修复 Fix Critical issues immediately
  2. Important问题在继续前修复 Fix Important issues before proceeding
  3. Minor问题记下留待以后 Note Minor issues for later
  4. 若评审者判断有误,附理由反驳 Push back if reviewer is wrong (with reasoning)

规则

  • 治理规则(跨节点,来自Red Flags):不得忽略严重问题 Ignore Critical issues

常见翻车

  • 常见翻车:以'太简单'为由跳过评审 Skip review because
  • 常见翻车:带着未修复的重要问题继续推进 Proceed with unfixed Important issues
  • 常见翻车:对有效的技术反馈进行争辩 Argue with valid technical feedback

治理约束

反驳评审意见必须附带技术理由 Push back with technical reasoning
反驳时应出示证明代码可行的代码/测试 Show code/tests that prove it works

◂push back时依据Red Flags准则 →
⇢评审者判断有误 →
⇢评审者判断无误,无需反驳 → END 推断
↻push back后请求澄清,重新与评审子代理沟通 → 推断
⦿处理完反馈后结束,返回上级任务 → END 推断

Integration with Workflows

语义/知识节点,不是流程步骤。

Subagent-Driven Development:

  • Review after EACH task
  • Catch issues before they compound
  • Fix before moving to next task

Executing Plans:

  • Review after each task or at natural checkpoints
  • Get feedback, apply, continue

Ad-Hoc Development:

  • Review before merge
  • Review when stuck
n05 · S 层 · 语义/知识 · governance

Red Flags

语义/知识节点,不是流程步骤。

Never:

  • Skip review because "it's simple"
  • Ignore Critical issues
  • Proceed with unfixed Important issues
  • Argue with valid technical feedback

If reviewer wrong:

  • Push back with technical reasoning
  • Show code/tests that prove it works
  • Request clarification

See template at: requesting-code-review/code-reviewer.md
